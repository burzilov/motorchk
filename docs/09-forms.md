# Формы заявок

Ядро принимает заявки с публичных страниц, сохраняет их в `submissions/` и отправляет письмо через SMTP.

## Meta формы

Файл: `content/forms/{id}.yaml` (только метаданные, без списка полей):

```yaml
id: contact
label: Обратная связь
subject: "Заявка с сайта: {{name}}"
success_message: "Спасибо, мы свяжемся с вами"
```

Плейсхолдеры `{{field}}` в `subject` берутся из имён полей HTML.

## Разметка в теме

```php
<?php Form::begin('contact'); ?>
  <!-- произвольный HTML: text, email, tel, textarea, select, checkbox, radio -->
  <input name="name" type="text" required>
  …
<?php Form::end(); ?>
```

`Form::begin` / `Form::end` добавляют CSRF, honeypot, timestamp и подписанный контракт полей (HMAC от разметки). Поля, добавленные JS после рендера, в контракт не входят.
Признак группы флажков определяется по разметке и сохраняется в подписанном контракте.

Подключите `/core/assets/js/forms.js` (см. `themes/example/partials/scripts.php`).

Эндпоинт: `POST /api/forms/submit` (JSON).

## Флажки (checkbox)

- Одиночный флажок сохраняется как `true` (отмечен) или `false` (снят) — независимо от `value`. В письме и в «Заявках» — «да» / «нет».
- `required` у флажка (согласие на обработку данных и т. п.) — заявка без отметки отклоняется с ошибкой «Обязательное поле».
- Группа флажков с одним `name` (или `name="…[]"`) — список отмеченных значений (`value`), в письме через запятую; ничего не отмечено — пустой список.
- При отправке без JS снятого флажка нет в запросе, отмеченный передаётся как `on` или `value`: `''`, `0`, `false`, `off`, `no`, `нет` и отсутствие поля — `false`; другие непустые значения — `true`.

## SMTP и заявки

Настройки SMTP и смена пароля админа — страница **Система**.  
Список заявок — **Заявки** (`/admin-panel/submissions`). Файлы: `submissions/{form_id}/*.json` (каталог закрыт от HTTP).

## Список в админке

У каждой формы своя вкладка и своя таблица. Колонки «Форма» нет: форма и так выбрана вкладкой. Фильтр по статусу письма (`sent`, `failed`, `pending`) остаётся. Новые заявки сверху (по имени файла, в нём дата). Страница по 50 записей, без потолка «только первые 200». Отдельной сортировки по столбцам, поиска и признака «непрочитано» нет.

Вкладка появляется, если выполнено хотя бы одно условие:

- есть `content/forms/{id}.yaml` (в том числе форма ещё без заявок);
- плагин зарегистрировал эту форму (`submissions()->registerForm()`, [10-plugins.md](10-plugins.md));
- в `submissions/{id}/` уже лежат заявки или пустой каталог — старый id без YAML не пропадает.

Один `form_id` — одна вкладка. Если плагин складывает все изделия в один id, в админке одна таблица, а не вкладка на товар. Ядро разные id само не склеивает.

Пока столбцы не настраивали и плагин не задал свои, таблица такая: **Дата**, **Почта**, **Открыть**. Плагин может задать столбцы по умолчанию (ключ в `payload` и подпись, в нужном порядке). Админ на той же странице включает и выключает поля, меняет подпись и порядок. Сброс возвращает столбцы плагина или, если их не было, снова только дату, почту и ссылку.

Настройка одна на весь сайт: `content/_submission-columns.json` (не в `content/forms/` — тот каталог только для публичных YAML — и не внутри файлов заявок). Она применяется и к старым записям. Сами `submissions/*.json`, подписи в контракте и страница одной заявки не меняются: карточка по-прежнему берёт подписи из контракта этой заявки.

Кандидаты в настройке: столбцы, которые зарегистрировал плагин, затем ключи из контрактов и `payload` уже сохранённых заявок. Нет ключа в конкретной заявке или значение `null` — в ячейке «—». `true` / `false` показываются как «да» / «нет», список — через запятую. Весь текст в таблице экранируется.

Сохранение и сброс — POST с CSRF, только после входа. Повреждённый файл настроек не перезаписывается; список заявок при этом открывается.

Антиспам: CSRF, honeypot, минимальное время заполнения, rate-limit 10 заявок/час с IP на форму. Капчи нет.

Если письмо не ушло, посетитель всё равно видит успех; в заявке будет `mail_status: failed`.
